**VideoHub AI 智能视频切片方案 · 最终提案 v2**

日期：2026-11-01。状态：方案完成，等待开发指令；本文不表示相关接口或功能已经实现。

本方案以当前工作区实际代码为基准，包括尚未提交的上传、存储、文稿复用和内容工作台改动。只新增本文，不修改业务代码、依赖、数据库、配置或前端，不调用付费模型。历史文档里的测试数量属于此前验收记录，不作为本轮测试结果。

**1. 决策与适用范围**

采用“文稿理解 → 候选生成 → 全局筛选 → 源视频校验 → 候选精细定位 → 边界复核 → 精选导出”。现有 FastAPI / PostgreSQL / Redis / Celery Solo / Protocol 适配器足以承接录播切片，无须先增加向量库、微服务或本地大模型。

首版面向访谈、播客、课程、知识讲解，以及这些内容的直播回放。输入包括公开免登录视频链接和已完成校验的私有视频上传。上传 MP3 / M4A 可生成文字层面的精彩片段建议，但视频导出必须有真实视频轨，明确拒绝纯音频生成视频；不生成静态封面伪视频。

正在进行的直播、游戏/体育等主要依赖画面判断的精彩瞬间、自动人物跟踪、竖屏重构图、字幕烧录、多个不连续片段拼接，分别留到后续阶段。首版每条成片对应一个连续源区间，保留原画面比例，默认 H.264 / AAC MP4，最高 720p 且不放大低分辨率来源。

默认推荐 3 条，最多 5 条；目标时长 30–90 秒，总选中时长最多 450 秒。目标是建议范围，最终硬上限按确认时的配置快照执行；质量不足允许少出或返回无合适内容，不强凑数量。免费/会员的 20/60 分钟、256/512 MiB、全局 5 GiB 等现有限制继续生效，不把数小时直播回放承诺为首版能力。

**2. 更新后的项目基线与修正**

| 已有能力及证据 | 对方案的影响 |
| --- | --- |
| `modules/uploads/`、`UPLOADS_V1.md`：私有上传、异步探测、用户级哈希去重 | 视频链接与上传统一进入来源契约；不重建上传服务 |
| `modules/video/sources.py`、`resolver.py`：SourceResolver、来源校验 | 分析入口复用来源抽象，不伪造平台 URL 或 ID |
| `transcript/service.py`、`BACKEND_FOLLOWUPS.md`：已授权文稿直接供 AI 使用 | 原文件失效后仍能分析文稿，但不能因此承诺可导出视频 |
| `storage/local.py`、`storage/retry.py`：持久化预留、文件读锁、最多 5 秒准入等待 | 撤回旧方案“媒体任务全程持有全局锁”的判断；仍保持单个 Solo Worker |
| `ai/repository.py`：cache_scope、精确文稿绑定 | 延续私有隔离；切片另外绑定时间轴及源媒体版本 |
| `tasks/repository.py`：终态 CAS、事务写入与额度结算 | 新增交付类型必须接入现有事务，不能只登记新 Task 类型 |
| `media/repository.py`：reusable 当前主要按 video_id 查询 | 必须增加媒体用途及覆盖范围，防止切片污染完整媒体复用 |
| `CONTENT_WORKSPACE_DELIVERY.md`：文稿、引用、上传与成果工作台 | 后续复用现有工作台，不另建一套产品入口 |

仍存在的缺口：千问 ASR 的时间轴是最长约 120 秒的上传分段，不是逐句对齐；当前解析器拒绝正在直播的链接；上传原文件尚无可供刷新恢复的鉴权流式播放接口。文档和代码冲突时，以实现与验证结果为准。

**3. 产品流程：分析与导出独立交付**

用户选择视频或已有文稿，确认分析报价，获得候选、原文证据、推荐理由和定位精度。用户选择其中若干条，确认导出参数与源文件可用性，再执行导出。后续可提供一键模式，但仍使用相同的两份交付契约。

分析输入为 `url / upload_id / transcript_id` 三选一。直接文稿入口验证归属、来源 ID、正文哈希和时间轴版本，不触发重新下载、重新转写或平台解析。无原文件也能交付文字层面的方案，并标注 `source_required`；粗时间轴标注 `needs_alignment`。

导出输入仅为已授权方案的精确 revision、1–5 个选中的候选 ID 和服务端输出档位。阶段 A 的分析版本保持不可变，选择通过导出请求表达；阶段 B 增加人工调整，调整起止时间形成新 revision，通过版本条件更新防止覆盖另一标签页的编辑。报价绑定 revision；修改后旧报价不能导出新范围。

对于上传，必须找到当前用户可用且内容 SHA-256 一致的上传实例，不仅检查相同文件名或 video_id。相同账号重新上传同一文件可恢复原来源；不同内容不得自动接替。公网来源可重新获取，但必须验证平台身份、时长与时间轴兼容性，无法确认时要求重新分析或明确失败。

首版不在分析成功后未经确认自动开启可能重新下载或调用定位供应商的任务。以后的一键确认必须展示并冻结完整预算，不在任务中等待用户输入。

**4. 候选生成与排序**

先复用确切文稿，否则字幕优先、ASR 兜底。已有总结只用于辅助了解主题，候选证据始终来自原文，不以摘要替代原文筛选。

文稿按语义单元分块，相邻块保留有限上下文；核心区与重叠区分开，统一原文编号以便去重。长文稿逐块产生候选，再做一次全局排序。不得只根据检索命中的少数片段宣称浏览了全文。

文稿细粒度足够时按 segment 编号引用；粗分段内可按确定性规则生成句子编号和字符区间，但这些句子继承粗定位精度，不用字数比例推算秒数。句子编号还要绑定原文校验值，重复台词依靠段落及位置区分。

模型返回原文编号、看点、内容类型、选择理由及评分，不直接决定任意时间戳。后端验证引用存在、连续、按序，文字与源文稿对应；标题与理由通过提示词约束和真实样本评审避免添加原文没有的事实。结构化引用校验不等于自动证明所有语义判断正确。文稿作为不可信素材放入模型上下文，不执行其中的指令、链接或命令。

建议以内容完整性、独立可理解性、信息价值、开头吸引力作为可版本化评分项；先做硬条件过滤，再按评分排序和主题多样性选择。模型分数是排序信号，不是“爆款概率”。时段重叠去重之外，还要去除不同时间重复讲述的同一观点。

不为了时长目标截断句子：必要时扩大到完整问答或故事闭环；超过上限则换候选或交由人工调整。排除指代不明、只有铺垫没有结论、必须依赖未包含画面的候选。纯语言模型无法保证识别所有画面依赖，因此真实样本验收必须包含这类反例。

对于无合适候选，返回结构化原因及 `outcome=no_highlights`，不是网络或模型故障。建议首版不核销用户 AI 次数，按独立“无交付”结算契约结束任务并释放占用；此规则仅针对新任务类型，不改变既有总结/问答逻辑。保留用户级负结果缓存和频率限制，避免相同输入重复消耗供应商费用。

**5. 时间轴与精细定位：正式导出的质量门槛**

时间数据区分 `coarse / segment / word / manually_reviewed` 等粒度及来源，不把 provider 名称等同于精度。可靠句级结果可用于初步定位，仍要检查是否存在字幕延迟、整体偏移、跨句范围和不合理持续时间。

现有 Qwen 转写可继续用于全文理解。对选中的少量候选，在带前后文的音频窗口中使用经过验证的句级/词级 ASR 或强制对齐适配器，映射回原媒体。只切小音频上传仍是粗定位，不能替代真实对齐。强制对齐不能纠正错误转写；匹配覆盖不足、文本冲突或边界歧义时标记不可靠。

定位信息保存为 clips 模块自己的派生时间轴，引用原 transcript_id，不覆写原转写分段，避免破坏已经交付的问答、引用或总结。用户认可的精确边界另存为人工版本，不伪装成模型结果。

媒体探测需要扩展到高精度 duration、音视频 stream start_time、time_base、旋转信息及流选择。现有上传探测主要提供取整后的计费时长，不能直接作为毫秒级剪辑依据。统一定义“源媒体播放时间零点”，记录提取音轨相对该时间零点的偏移；窗口偏移、音轨偏移分别处理。

变帧率按媒体时间戳定位；不能用帧号除固定帧率。片段输出使用统一时间基准归零，并保留音视频原有相对偏移，避免分别归零造成不同步。不要求整段视频预先转码。

精细定位后重新检查时长、句子完整性、相邻重叠与目标内容；边界变化可能使原本合法的候选不再合格。无可用定位能力时仍可交付带粗定位说明的分析方案，但自动精准导出明确返回 `CLIP_TIMING_UNRELIABLE`。只有经过预览确认的人工区间才可走人工模式，不静默降级为粗切。

定位供应商采用独立 Protocol 与能力声明，不把兼容 `verbose_json` 的请求格式等同于所有模型都支持时间戳。第一开发阶段需用真实样本确认当前可用供应商；M1 8GB 不默认安装 PyTorch 或本地大模型。供应商选型与效果是上线门槛，不在方案阶段冒充已验证能力。

**6. 模块与数据契约**

新增 `modules/clips/`，持有以下数据；具体 SQL 字段和迁移编号在开发时按当前 head 确定。

| 数据 | 关键内容 |
| --- | --- |
| ClipPlan / revisions | owner、video_id、精确 transcript_id、原文/时间轴哈希、策略参数、模型与提示词版本、候选、usage、任务 ID |
| ClipTimeline | 源媒体指纹、时基映射、候选窗口、精细定位、provider/模型/版本、质量及不确定原因 |
| ClipExport | owner、plan revision、选定项与范围、输出 profile、任务 ID、提交状态及成片清单 |
| ClipExportItem | 候选 ID、最终源区间、file_id、定位版本、源指纹、输出时长及验证结果 |

跨模块通过明确契约访问：TranscriptService 负责文稿授权，SourceResolver / UploadService 负责来源，MediaService / Repository 负责媒体登记及有效性，TaskService / Repository 负责编排及事务，BillingService / Repository 负责报价和核销。

新增或扩展 `ClipSelectionProvider`、`ClipTimingProvider`、`ClipRenderer`、`ClipSourceProvider` / `ClipMediaProbe` 的 Protocol。复用现有 LLM 传输和预算；扩展明确的 purpose/schema 校验，不把切片伪装成 summary 请求。FFmpeg 与模型调用均不出现在 router 中。

**7. 必须先解决的源文件与成品隔离**

当前 MediaRepository.reusable 按 video_id 查找，AudioAcquirer 会从可复用媒体提取音轨。切片和原视频关联同一个 video_id 是正确的，但仅凭该字段判断可复用完整媒体会出错。

为媒体增加用途与覆盖范围，例如 `full_source / full_audio / clip`，记录源指纹、完整性、源区间和时基。完整媒体复用契约只返回经过验证的完整源或完整音频；局部切片不参与后续全文 ASR、音频提取、原视频缓存命中或完整源选择。检查所有现有调用点，不能只修新增 clips 模块。

旧媒体采用兼容迁移，不直接假定所有历史记录都完整；根据历史任务类型与 Worker 内探测确认可复用性。用途字段不得由用户传入。上传原件仍由 uploads 模块管理，不额外复制成公开 media 文件。

**8. 任务编排、导出一致性与崩溃恢复**

新增 `ai_clip_plan` 和 `clips_export`，均通过统一 TaskService 创建，Celery 中执行。保留一个 `--pool=solo -c 1` Worker。一个导出任务处理最多 5 条选中片段：一次获得源视频、一次准备必要定位窗口、逐条导出；不创建后再等待 Solo 子任务，也不重用现有下载 Worker 来启动另一个顶层任务。

分析复用 TranscriptionPipeline 的内部业务契约；导出通过来源适配器调用下载/读文件能力，而不是调用下载 HTTP 接口。内部任务阶段与顶层 Task 状态分离，新增 stage 即可，不为每一步新增全局状态枚举。

SSE 沿用先订阅后快照、seq 去重和 500–1000ms 节流；阶段可为 acquiring_transcript、selecting、ranking、preparing_source、aligning、rendering、validating、committing，存储准入等待复用 waiting_for_storage。进度只能单调增加，完成以 PostgreSQL 为准。

首版选择“整批原子交付”：全部选中片段导出并通过校验后，再登记所有文件、导出关系、授权、任务完成及核销。任何单片失败均不公布新成品，任务失败；不新增部分成功状态。方案和已确认可复用的派生定位可保留，用户可以选择更少片段重试。后续确有需求再增加逐片持久化与部分交付。

本地文件系统与数据库不能真正形成跨系统原子事务。先用确定的 file_id 暂存/提升文件并持久化提交清单，再在 complete_with 的数据库事务登记；只有完成事务后才可分发。取消获胜时不登记结果。若数据库提交结果不明，先核对最终任务和文件登记，不盲删可能已成功交付的文件。

恢复程序根据任务、提交清单、媒体登记和进程存活情况核对：完整成功不重复执行或扣费；已确认未提交的孤立成品才清理。源或子进程状态不明时保留文件与相关容量保护，标记需核实。不得按 TTL 直接释放仍可能存活任务的资源。

重复消息由任务启动 CAS 阻止重复工作；确认同一 quote 返回同一 task；同用户相同导出规范的活动请求合并到同一任务或明确冲突，不并行重复渲染。进程崩溃后的失败需显式重试，不自动无限重跑。

**9. 容量预算与执行限制**

复用持久化容量预留和源文件共享读锁。容量估计包含源视频下载的同时存在文件、音频/定位窗口、所有待交付成片以及编码临时文件；已经存在的源文件不重复预留。云调用前做相应的资源准入检查，实际写入期间仍检查容量。

预留量是任务整体峰值，单文件上限与任务临时目录总上限分开。现有 MAX_FILE_SIZE_MB 不能直接套成“源文件+5 个成片”的总预算，也不能为切片功能全局放宽旧任务限制；新增导出专用上限，并受全局配额约束。

多个文件逐个从 tmp 提升至 files 时，现有预留按 tmp 路径计算未写入量，可能产生重复计入。导出提交需要通过 StorageAdapter 的短锁批量提交契约，原子调整预留占用并登记文件清单，避免低估或重复占用；不恢复全程全局锁。

上传原件复用 uploads 文件锁，普通源媒体复用 storage 文件读锁。取得锁后重新检查文件状态、大小、指纹及有效期，避免查询后被清理。到期源在已经开始读取时按现有保护机制处理；排队不意味着永久延长原文件保留时间。

建议初始预算如下，均需真实样本测量后校准，属于方案配置，不是现有配置或性能承诺：

| 项目 | 初始建议 |
| --- | --- |
| 分析总时限 | 900 秒，包含必要转写 |
| 导出总时限 | 1800 秒，包含源获取、定位、渲染和校验 |
| 源下载 | 不超过现有 600 秒及剩余任务预算 |
| 定位网络阶段 | 总计 180 秒；连接 5 秒、有限读取超时，均不超过剩余预算 |
| 精细定位音频总量 | 去重后的窗口最多 900 秒；供应商单次体积另行限制 |
| 单片渲染 | 最多 180 秒并受剩余总时限约束；片数最多 5 |
| FFmpeg | 一个渲染进程，默认 1 个编码线程 |
| LLM | 文稿最多 60000 字符，最多 16 逻辑调用、累计 16384 输出 Token，每次最多 4096 |

所有阶段使用同一剩余 deadline，不因重试重置总预算。LLM 调用预算预留全局排序和最多一次结构修复所需空间，输入上下文也限长；不能每个候选单独无限评审。HTTP 只对可重试网络错误、429、部分 5xx 最多重试一次，计入时间和供应商请求用量；FFmpeg/ffprobe 不自动重试。

本地进程继续独立进程组、500ms Watchdog，检查取消、总超时、任务体积及全局容量。TERM 后必要时 KILL，确认进程树退出才清理。不能依赖 revoke(terminate=True) 或 Solo 的软硬超时。

**10. 缓存、授权与多文件访问**

首版分析方案采用用户级范围，即使公网内容相同也不共享用户的目标、编辑和方案。后续如共享公共计算缓存，必须与交付授权分开设计。

分析键包含 user/cache_scope、source video_id、精确 transcript_id、正文哈希、规范化的原分段时间轴哈希、标准化策略参数、LLM 逻辑模型、prompt/schema/策略版本及输出语言。正文相同不能替代时间轴相同。

精细定位键包含用户范围、源文件内容指纹、原文引用及窗口范围、时基映射版本、定位 provider/model/version。导出键包含源指纹、最终区间、精细时间轴或人工 revision、编码 profile、renderer 版本。更新文字标题不应让相同成片重新渲染；修改真实区间则必须失效。

旧成片仍有效时，重复请求复用原 file_id 和原 expires_at，不能借缓存命中无限延长保留。已过期成片可在原视频仍可用且通过准入后重新渲染；不重复分析全文。原件、成片、文稿、方案各自保留生命周期，删除原件不级联删除已交付文字和有效成片。

目前任务授权和免费复用判断主要识别顶层 file_id / result_id / transcript_id。新增 clip_plan_id / clip_export_id 必须扩展权威识别，避免因已拥有 transcript_id 误判新方案免费。

多文件权限以 ClipExportItem → ClipExport → 已成功且属于当前用户的 Task 为依据，通过 Repository 契约纳入现有 TaskService.authorize_file；不只在 JSON 里放 file_ids 数组便假定已有授权。旧 file_id 下载仍兼容。方案读权限也由归属和成功交付决定；不能凭公开 video_id 或可猜 UUID 访问他人私有方案。

成片分发复用短期用途凭证、Range 与实际下行流量记账。不得在 URL 中放完整登录 JWT，原始上传目录不静态公开。

**11. 额度与成本：推荐的首版规则**

分析与导出均走报价确认，不能用旧直接创建接口绕过。任务快照冻结模型、策略、精度模式、revision、范围、片数、质量档位、用户最大扣量和处理预算。源码配置变化不能让旧报价换成另一种产品。

导出必须重新验证当前源视频的真实时长、体积、视频轨和当前媒体权益，不能沿用文稿分析入口的 duration_seconds=0 或 text_only 豁免。原件准备后、首次付费定位前再次确认；无法确定源或权益不符时失败，不把文稿授权当作重新获取完整视频的权限。手工边界也必须有限、按序且处于可播放源范围内。

| 操作 | 推荐用户额度规则 |
| --- | --- |
| 新分析成功交付非空候选方案 | 1 次 AI；需要首次 ASR 时按完整音轨时长核销一次 |
| 复用已获得文稿或字幕 | 0 转写秒；新分析仍按新交付判断 AI 次数 |
| 本人同版本方案复用 | 0 AI、0 转写秒；必须仍可验证授权与原结果 |
| 分析无候选、失败、有效取消 | 新任务零核销；成功前的中间缓存不等于已经购买 |
| 已有方案的导出或区间调整后重新导出 | 0 AI、0 全文转写秒；仍受渲染次数、时长、资源、频率和流量限制 |
| 新策略/目标引发重新理解全文 | 新分析报价，不把它伪装成免费导出 |

精细定位有供应商成本，不等于重复进行用户购买的全文转写。首版将有限窗口定位作为切片导出的内部处理成本，单独记录真实供应商用量，并通过窗口总量与导出频率约束；不调用现有 record_asr 把局部定位记成整段 ASR 或多次扣分钟。

建议每个方案 revision 每日最多 3 次新渲染，且每账号每日最多 10 个新导出任务；缓存读取不占渲染次数，真正开始的导出占次数，失败/取消不返还防滥用频率。现有每小时 60 个新任务、最多 10 个未终结任务继续约束。免费导出是有限资源权益，不承诺无限计算；这些数量属于待实施的策略常量。

新任务的内部拉取源视频属于已确认切片操作，不隐式创建一个用户可下载的完整原视频产品，也不二次扣现有免费“原视频下载次数”；仍执行当前媒体权益限制和出站流量规则。报价应清楚展示“分析交付”与“成片交付”，避免用户误以为 1 次 AI 保证找出 5 条爆款。

终态、核销/零核销释放、结果登记在同一数据库事务完成。空结果的新结算路径必须显式传递经验证的交付结论，并受 task_type 限定；不能沿用所有 completed 任务必扣 AI 的分支。

若尚未发布新报价规则，功能应通过默认关闭的 feature flag 保持不可创建收费任务，不以零额度快照接入后再补账。上述为本方案推荐规则，正式对外发布不在本轮授权范围。

**12. API 草案与前端衔接**

以下均为拟新增接口，尚未实现；全部挂载 `/api/v1`，统一 data/error/request_id，始终要求登录。

| 接口 | 契约 |
| --- | --- |
| POST `/clips/plans/quotes` | 三选一来源 + 切片策略；返回分析报价；确认复用 `/billing/tasks` |
| GET `/clips/plans/{id}` | 已交付候选、引用、定位粒度、revision、源可用性；不保证此时源文件被长期占用 |
| PATCH `/clips/plans/{id}`（阶段 B） | 编辑人工边界等允许字段，以 expected_revision 条件更新；新语义策略另建分析 |
| POST `/clips/exports/quotes` | 精确 plan revision + 候选 ID + 服务端 profile；返回导出报价及硬预算 |
| GET `/clips/exports/{id}` | 已交付成片、最终时间范围、file_id、有效期和验证结果 |
| 现有 `/tasks/*`、`/files/*` | 进度、取消、文件凭证与下载，扩展新结果类型和多文件授权 |

保持现有 AIInputRequest / 旧 billing action 兼容；新切片报价使用独立严格 schema，不让 clips_export 套上 ai_summary 的模型、ASR、结算和文字入口假设。请求只接受 ID、结构化参数和服务端档位，不接受本地路径、任意 FFmpeg 参数、用户代理或 Cookie。

后续前端在现有工作台增加切片入口，复用引用抽屉、任务历史、上传恢复、额度确认和错误通知。首版先交付后端 Swagger/curl 闭环，未获下一阶段指令不修改 frontend。

人工精调依赖可靠的源视频预览。上传原件当前只靠浏览器本地对象 URL，刷新后不可恢复；人工精调阶段需要另行补充鉴权、Range、短期凭证、流量记账和读取锁的源文件播放能力，或提供明确且安全的兼容转码预览。MOV/MKV/WebM 不保证浏览器原生播放，不能只添加一个 video 标签就视为完成预览。

**13. 三轮自我审查记录与已纳入的修订**

| 轮次 | 审查问题 | 最终处理 |
| --- | --- | --- |
| 第一轮：项目适配 | 旧方案缺少上传来源，且仍认为长任务持有全局存储锁 | 接入统一来源；复用预留与文件锁；保留单 Worker，撤回旧判断 |
| 第一轮：成果生命周期 | 原件已删但文稿仍在，能否继续用？音频上传能否导出视频？ | 分析与导出解耦；文字成果可读可分析；真实视频轨是视频导出前提 |
| 第二轮：选片质量 | 粗时间轴、摘要漏证据、跨块截断、模型编造秒数 | 原文引用、重叠分块、精细对齐、精度标记及导出前边界复核 |
| 第二轮：时间正确性 | 音轨偏移、取整时长、变帧率及字幕延迟 | 新增精确媒体时基映射，不用计费秒数或固定帧率切片 |
| 第二轮：复用正确性 | 同 video_id 的切片会被下次转写当作原片 | 增加用途及覆盖范围，完整源查询排除切片并回归既有调用方 |
| 第三轮：原子交付 | 5 条中 1 条失败、取消与完成竞争、数据库提交不明 | 首版整批交付、提交清单、CAS 事务、核对后清理，明确不承诺部分成功 |
| 第三轮：额度与权限 | 仅返回 file_ids 是否可下载？已有文稿是否让新方案误判免费？ | 导出关系作为文件授权依据；结算优先新交付 ID，扩展历史/后台引用 |
| 第三轮：资源成本 | 多文件提升后预留重复计算、免费导出无限调用定位服务 | 批量提交容量契约、窗口/渲染次数预算、真实用量记录与入口限流 |
| 第三轮：可实施性 | 没有已验证的对齐模型，也没有刷新后预览，是否仍承诺精准切片？ | 供应商精度验证作为上线门槛；不可靠时阻止自动导出；人工模式等预览能力后实施 |

上述审查是设计与代码静态核对，不等于对新功能做过自动化或真实模型验收。后续发现新证据时继续修订，不将“最终提案”解释为零风险保证。

**14. 分阶段实施与验收门槛**

阶段 A：切片后端闭环。内部顺序是先验证时间轴供应商和媒体时基，再实现源/成品隔离、分析方案、导出与事务/权限/额度集成。交付公网视频、私有视频、已有文稿分析，最多 5 条连续片段、受控下载与清理。所有修改限 backend；如需同步配置模板，先按项目授权范围处理，不借本阶段改前端。

阶段 B：审阅与成片体验。获得单独指令后接入工作台、可靠预览与人工精调；字幕包装、画面比例转换按需求独立验收。音频剪辑可复用分析与定位契约，但另定义音频产品、格式和交付行为。

阶段 C：实时直播。独立采集进程负责有限时长录制与分段落盘，统一 TaskService 调度增量短任务；采集不长期占住唯一分析 Worker。需要流中断/重连、断点时间映射、窗口重叠、全局去重、积压控制、滚动保留及读保护。所有平台拉流仍经适配器与公网安全校验。先测量吞吐和供应商延迟，再确定可承诺的延迟，不直接解除 is_live 拦截。

阶段 A 必须覆盖以下验收，而非只测试 JSON 字段：

- 真实 FFmpeg/ffprobe 固定样本：非关键帧边界、音画起始偏移、变帧率、旋转、坏文件、过期源、无视频轨、成片时长与解码有效性。
- 私有授权与缓存：跨账号拒绝；同文不同时间轴不串用；相同源重新上传可恢复；错误源不可替代；切片成品不会被完整转写复用。
- 任务/账务：重复报价确认、重复消息、同请求合并、取消/完成竞争、无候选零核销、导出失败不重复扣分析、已有 transcript_id 不误判新方案免费。
- 多文件提交：渲染中途失败、提升到一半崩溃、数据库提交结果不明、已完成结果重试；授权和资源清理均与最终状态一致。
- 存储：预留不足在付费调用前拒绝、提升期间预算不重计、读锁阻止清理、无法确认进程退出时保留资源、超过 100 条过期记录不漏清。
- SSE/入口：先订阅后快照、seq 去重、重新连接、进度单调、waiting_for_storage 可取消；未登录、越权和绕过报价均失败。
- API 与真实 Celery Solo 集成：独立 PG schema / Redis / 存储目录，不写业务数据，不用 mock 结果宣称真实识别有效。

真实效果另做小规模评测：建议准备至少 12 段获准使用的视频，覆盖中文、英文、多人对话、背景音乐、长停顿、重复观点、画面依赖和无精彩内容反例。先人工标注可接受区间，再与无 LLM 的规则基线比较。

建议上线质量门槛：人工独立复核的推荐接受率达到 80%，不截断词句及关键上下文的比例达到 95%；人工标注有合适内容的视频中，至少 75% 能返回一条被接受的候选，防止靠少出或不出来抬高接受率。单独报告无精彩内容样本的误选、重要观点漏选和画面依赖误判。指标分别计算并报告分母、样本量及标注差异；12 段只是首轮验证起点，不把小样本比例当作普遍效果保证。

对连续语音固定样本，技术边界误差目标为 0.5 秒以内；技术边界精度不等同于人工对“精彩片段”区间的一致判断。不满足时只发布带复核提示的候选方案，不宣称自动精准剪辑达标。

同时记录冷/热缓存端到端耗时、排队时间、峰值 RSS、磁盘峰值、定位音频秒数、LLM 输入/输出 Token、供应商请求与估计成本。当前方案不宣称 M1 上的真实处理速度或单位成本，预算常量在评测后校准。

每个获准开发阶段完成后运行 `cd backend && uv run pytest`，有迁移时执行 `uv run alembic check` 并在隔离 schema 验证；输出修改文件清单、API/Worker 启动命令、Swagger/curl 步骤及实际测试结果。未经指令不跨阶段。

**15. 最终建议**

以阶段 A 为下一次开发范围：新增 clips 业务模块，复用现有上传、文稿、任务、存储和模型能力；先分析后导出，完整源与切片严格区分，精准定位作为正式自动导出的门槛。第一阶段不引入向量库、多 Worker 或实时直播，不重写现有知识库。

方案层面已经确定架构、失败语义、缓存隔离、资源预算和推荐额度规则；仍需在实施与上线验收中获取的证据是定位供应商能力、真实选片效果、M1/部署服务器性能和成本。它们是明确的验证门槛，不是已完成的功能。
