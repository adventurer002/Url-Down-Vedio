# VideoHub AI 性能与长视频处理统一方案

版本 V2.1，部署基线为轻量云 4 核 / 8GB / 10Mbps。A、B、C 包已完成本地实现与回归。D 包已实现计时和多账号容量脚本，真实云内上传及目标机承载范围待实测。见 [性能 D 包](PERFORMANCE_D.md)。

本文件替代此前逐轮追加的下载、双 Worker、多用户和长视频专项草案。A 包说明见 [PERFORMANCE_A.md](PERFORMANCE_A.md)。B 包说明见 [PERFORMANCE_B.md](PERFORMANCE_B.md)。C 包说明见 [PERFORMANCE_C.md](PERFORMANCE_C.md)。生产启用等待确认。

## 1. 推荐结论与成功标准

采用 **按阶段执行的 Celery 流水线 + 云端 ASR/LLM + 多级结果复用 + 同云同地域对象存储分发**。继续使用现有 FastAPI、PostgreSQL、Redis、yt-dlp 和 FFmpeg，按现有 4 核 / 8GB / 10Mbps 机器配置，不以升级服务器作为本轮前提。

优化顺序是：修正冲突超时 → 分阶段并行与结果复用 → 尽早将文件分发迁到对象存储 → 减少重复取源和转码 → 用真实多用户负载确定容量。10Mbps 条件下，文件分发与缓存优先级高于继续堆 Worker。

用户应得到的行为：

- 不同用户的下载、转写、总结和问答可以同时推进，下载不会占住纯文本 AI 的执行槽。
- 长视频显示已完成分片；单片失败只补做失败片，后续总结失败不丢弃已完成文稿。
- 已有成品或 AI 结果直接复用，不重新处理。
- 页面断连不终止后台任务，重新查询可恢复进度与结果。
- 在实测可承载的目标负载内降低等待；请求受理快、实际开始快和处理完成快分别验收。

Worker 数、10Mbps 出口、5GB 本地空间、源站限制和模型配额一起决定容量。首期按 1/2/5 用户逐档测试，再测 10 人突发的等待与恢复；20 人留作后续扩容测试。缓存用户和纯文本 AI 用户不与完整视频取源、转码用户按同一成本计算，不把“十人在线”写成“十个长视频同时无等待处理”。

## 3. 唯一目标架构

~~~mermaid
flowchart LR
    U[用户请求] --> API[FastAPI / TaskService]
    API --> C{已有结果}
    C -->|命中并授权| R[返回结果或文件访问地址]
    C -->|未命中| P[PostgreSQL 保存任务与阶段]
    P --> Q[Redis / Celery 分阶段派发]
    Q --> S[control：元数据与取源]
    Q --> M[media：视频或音频传输]
    Q --> A[asr：远程语音转写]
    Q --> L[llm：总结 / 问答 / 思维导图]
    Q --> V[render：音频预处理与视频重处理]
    S --> P
    M --> P
    A --> P
    L --> P
    V --> P
    P --> E[进度快照 / SSE / GET]
    M --> O[成品上传对象存储]
    V --> O
    O --> R
~~~

图中阶段按业务依赖执行，不是全部串行：已有文稿直接进入 AI；有字幕时跳过音频下载与 ASR；原生兼容 MP4 跳过重转码；各阶段完成后再派发下一阶段。

### 3.1 阶段执行规则

- 外部始终保留一个用户任务 ID，内部使用阶段记录，不为每段创建一个用户可见任务。
- 阶段保存状态、执行标识、输入/处理版本、结果引用、已完成分片、尝试次数与截止时间。
- 执行成功后，在数据库短事务内提交结果与下一阶段待派发状态，再发送消息。沿用现有恢复进程补发未成功派发的阶段，避免数据库提交与消息发送之间丢工作。
- Worker 完成当前阶段即释放槽位，不同步等待另一队列的 Celery 结果，不在网络传输期间持有数据库事务或全局存储锁。
- 重处理完成后由 render 登记待上传阶段并释放 CPU 槽，交给 media 执行上传；不能让慢公网上传继续占住重转码 Worker。
- 阶段领取使用现有行锁/CAS 思路，重复消息不重复领取同一执行。权益按用户任务预留并只结算一次，中间重试不重复扣用户额度。供应商请求超时后的执行结果可能不明，无法承诺外部供应商绝不重复计费；支持请求幂等键时使用它。
- 缓存命中由 TaskService 在短事务内完成授权和权益处理，不占耗时阶段槽位。ASR 分片和 LLM Map/Reduce 节点作为内部执行单元完成后释放槽位，按父任务的有效并发补派下一单元，避免一个长任务一次性占满队列。
- 单用户并发名额属于用户业务任务；CPU、网络和模型名额属于当前执行阶段，不能把名额永久绑定给等待中的中间阶段。
- 所有入口共用阶段路由，包括 billing.execute、普通业务入口、缓存命中、取消与故障恢复，避免一部分任务继续走旧串行链路。

### 3.2 五类执行资源

| 队列 | 职责 | 正式部署压测起点 |
| --- | --- | --- |
| control | 元数据、短链接、平台来源描述；缓存不命中才取源 | 1 个 Solo Worker |
| media | 视频/音频传输、轻量封装、成品上传 | 2 个 Solo Worker |
| asr | 已准备音频的远程分片转写 | 1 个 Solo Worker |
| llm | 已准备文本的总结/问答/思维导图 | 1 个 Solo Worker，纯文本压力测试后再考虑增至 2 |
| render | 音频切片/解码、视频转码、剪辑渲染 | 1 个 Solo Worker，重处理先用 2 个有效线程 |

这是当前 4 核 / 8GB 机器的压测初值，共 6 个轻重不同的 Worker 进程，不对应六个 CPU 重任务。取源、媒体和远程模型阶段主要等待外部 I/O，重 CPU 阶段同时 1 项。每个继续使用 --pool=solo -c 1，并有独立节点名和服务实例；保持 worker_prefetch_multiplier=1，避免一个 Worker 提前占走多项工作。

control 与 media 分开，保证已有下载不会把新链接的取源入口完全占住。control 初始只有一个槽仍会在大量冷取源时排队，后续按来源耗时与源站限制扩容。浏览器初始同时 1 项；普通平台取源初始同时 2 项，实际受 Worker 槽位约束。

ASR 与 LLM 从正式架构开始就分开，确保长语音转写不占住文本问答的执行槽。同任务分片并发初始为 1；长总结每个 Map/Reduce 单元完成后释放 LLM 槽。先测 1 个 LLM 槽，若文本等待明显且内存、外部模型配额有余量，再增加第 2 个 LLM Worker，优先让不同用户共享容量。正在执行的单次外部调用无法被新请求无损抢占，排队目标按真实负载验收。

## 4. 下载与缓存：优先消除重复工作

### 4.1 查找顺序

每次提交先查已完成结果，再查已完成的中间结果，最后访问来源并执行缺失阶段。

- 成品：视频身份 + 下载档位/实际画幅与流选择 + 输出处理版本。
- 字幕/转写：沿用 video_id + source_type + language + content_version + asr_model。
- AI：沿用 transcript_content_hash + llm_model + prompt_version + output_language。
- 思维导图：沿用 source_content_hash + schema_version + llm_model。
- 分段检查点：来源内容身份 + 片段边界 + 模型/语言 + 处理版本。阶段重试先读取匹配检查点。

公共资源复用时，为当前用户建立访问授权并沿用权益口径；不能直接借用另一个用户的任务归属。私有上传保持用户隔离。来源可能更新且没有可靠版本时，使用有界有效期或重新确认，不能宣称视频 ID 永远代表不变内容。

先做已完成结果复用。只有重复同内容并发确实占用明显资源时，再增加正在执行工作的合并：各用户保留独立任务和订阅关系，单个用户取消不终止其他用户仍需要的共享工作。该功能不是首期并发上线的前置条件。

### 4.2 来源缓存

来源描述进入服务端 Redis，最长 120 秒，且不能超过媒体地址有效期；键包含视频身份、取源后端版本和出口配置版本。Worker 检查身份、档位和有效期后传输，不再次解析整页。

必须确认媒体访问所需的会话、请求头和出口可复现；无法复现会话的来源继续走受控重新取源，不盲目复用 URL。媒体地址不进入公开响应或日志。实际连接、DNS 和重定向仍走现有公网检查。

缓存缺失时正常取源；已确认地址失效时最多刷新一次。风控、验证码、登录限制和 429 不作为“地址过期”反复重试。来源缓存不可用可回退正常提取，任务编排本身仍依赖现有 Redis。

### 4.3 传输与封装

- 同档位优先 H.264/AAC；补齐可靠编码识别，保留现有复制合并。
- 已满足轨道、容器及播放约定的合流 MP4 直接移动交付；需要 faststart、合并或修正容器时继续 FFmpeg，避免降低现有播放能力。
- 独立音视频最多同时两路。每个 media Worker 所有流合计最多 2 个分片请求，两名传输 Worker 合计最多 4 个；设置并发时核对源站与总体带宽，不创建范围切片下载器。
- 不假定源视频入站也只有 10Mbps：轻量云套餐中的 10M 通常指公网出站，实际以厂商规格与测量为准。两个媒体槽先并行获取来源，但成品公网传输与 ASR 上传共享出口预算；不再通过扩大分片并发争抢同一出口。
- 两路同时下载时，通过两个独立受控子进程实现，避免共享修改 yt-dlp 参数、socket 补丁或进度计数；都纳入同一阶段的进程控制与体积预算。每个实际网络连接继续经过既有适配器。
- AI 优先字幕、再取独立音轨、再使用已缓存本地媒体。若来源只有合流视频，按既有支持策略处理，不能悄悄下载整片而仍按音频预算报价。
- 整文件解码用于交付验收，正常请求路径不增加逐帧校验或全文件哈希扫描。

## 5. 长视频：统一预算与可恢复分段

### 5.1 支持范围

首期修复现有权益范围内的 20/40/60 分钟视频。免费 20 分钟、会员 60 分钟、文件大小和每日额度维持现有业务规则；同账号下载并发建议免费 2、会员 3，AI 类并发建议 2，并受实际系统容量约束。

6 万字符、16 次模型调用和总输出 token 预算要在执行规划时一起检查。6 万字符以内也不代表一定不会超模型预算。支持范围外在确认前给出明确提示；如要支持两小时以上视频，另行调整支持范围、模型预算及存储容量。

### 5.2 一套截止时间，避免层层提前截断

任务确认后记录整体截止时间；每阶段执行时记录阶段截止时间，每次外部调用使用两者剩余时间中的较小值。阶段排队不消耗单次 HTTP 请求预算，但计入任务生命周期和用户等待；阶段重试、退避、地址刷新不能重置整体截止时间。

| 预算 | 建议起点与约束 |
| --- | --- |
| HTTP 受理 | 快速创建任务；不会等待完整取源、ASR 或 LLM |
| 元数据取源 | 后台 45–60 秒，同步对齐平台内层预算；不能只改最外层 |
| 连接 | 5–10 秒，继续有界 DNS/连接检查 |
| 单次 ASR / LLM | 总预算先测 180 秒；读取无数据预算先测 120 秒；所有尝试共用总预算 |
| 音频上传 | 按字节与实测上传速率估算写入预算，受单次总预算约束 |
| 音频预处理 | 按输入时长估算，60–180 秒作为测试起点，替换固定 30 秒 |
| 下载 / ASR / LLM 阶段 | 按文件大小、片数、有效并发和实测耗时估算，分别受阶段上限约束 |
| 整体生命周期 | 处理流程先测最高 2 小时；这是执行上限，不是新的视频时长权益 |

阶段预算采用可检查的简单估算：分段阶段取“准备开销 + 向上取整(分片数 / 有效并发) × 单片实测 p95 × 1.5”；下载取“准备开销 + 预计字节数 / 保守实测速率 × 1.5”。估算值受阶段上下限及整体剩余时间约束，缺少观测数据时使用现有有效配置作为初值。

阶段硬上限压测起点为：下载 3600 秒、ASR 3600 秒、LLM 1800 秒、单项重处理 1800 秒，整体仍不超过 7200 秒，不能把这些上限简单相加当成用户承诺。任务规划已明显超出支持预算时在确认前返回明确原因；模型调用次数与输出预算也在同一步检查，并为最终 Reduce/思维导图预留额度，避免前面 Map 消耗全部 token。

明确替换原 AI 整条链路固定 900 秒的截断方式；下载与重转码分别计时。预算估算采用简单公式与观测值，不建设预测调度系统。所有上限与父子剩余预算统一从配置和阶段计划生成，杜绝散落的短硬编码继续提前中止。

已有 /videos/parse 契约不静默改变。新增异步解析入口，缓存命中返回现有结构，未命中返回 202 + task_id；通过明确的新请求/响应模型提供给后续调用方，不让同一旧接口无说明地改变返回类型。本轮实施验证先使用 Swagger/curl，frontend/ 的后续接入遵循获准开发阶段。

### 5.3 分段与恢复

- 千问已有最长 120 秒音频分段，复用并抽出阶段进度；通用 OpenAI 兼容 ASR 补充分段适配，不能只提高整文件上传上限。
- 音频分片同时满足供应商时长、字节和上下文限制；时间戳按原视频位置合并。每片完成即保存小体积检查点，保存在有配额/生命周期管理的持久位置，不仅放在失败后删除的任务目录。
- 保留 Map/Reduce，总结按模型 token 上下文规划。持久化每片摘要及每层归并结果，继续处理缺失节点，最终思维导图读取已完成总结。
- 检查点只表示部分工作完成；全部必需阶段成功后才标记用户任务完成。已存文稿不因后续 LLM 超时被删除。
- 对可恢复网络错误最多补试一次；在明确重试层执行，移除对应下层的叠加重试。耗时已接近截止时直接结束并保存检查点，供应商不支持幂等的付费超时请求不盲目补发。
- 显示“转写 8/30 段”“总结 3/5 段”等真实进度。错误区分取源、下载、预处理、ASR、LLM、整体截止、业务超限与模型预算不足。

## 6. 存储、分发与最少必要控制

### 6.1 本地只保留必要中间件

保持 STORAGE_MAX_QUOTA_MB=5120、本地最小空闲空间检查与 24 小时成品/文件过期策略。按阶段峰值预留源文件、音频分片、转码输出和在途写入余量，不能用单个成品上限代替峰值预算。

Watchdog 每 500ms 保留取消、总超时和当前阶段体积检查。全存储目录遍历从循环移至准入、提交和定期校准；运行期间用原子配额预留与阶段写入量记账，disk_usage 提供空闲空间检查。计数不确定时重新校准，不放行超额任务。

阶段完成后释放不再需要的中间件；本地剩余空间不足时明确等待资源。5GB 是实际容量约束，增加 Worker 不会增加空间；在多任务压测中记录峰值，而不是仅检查成品大小。

沿用短配额/提交锁：成品移动、数据库登记和清理之间要有明确的发布边界，防止并发清理误删未登记成品。清理跳过活动执行目录与仍被读取的缓存文件，不在外部传输期间占全局锁。

### 6.2 对象存储直接分发成品

正式多用户服务采用 Protocol 存储适配器对接同云同地域对象存储，私有对象由 API 鉴权签发短时下载地址。API 负责授权，浏览器直接从对象存储传输文件；热点访问再接 CDN。该项在当前 10Mbps 机器上提前实施，不等到大量用户排队后再处理。

C 包使用独立网关读取私有对象并向浏览器传输，以一次性 Range 凭证和实际字节回报沿用现有用户流量额度。网关需要独立出口。本地成品先可用，后台镜像验证后转入网关，保留本地副本用于回退、转写和剪辑。具体启动和验收边界见 [PERFORMANCE_C.md](PERFORMANCE_C.md)。

迁移顺序为“本地生成 → 上传完成 → 登记可用对象 → 提供下载地址 → 释放可清理本地副本”。上传失败不能宣告文件已交付，上传要计入阶段预算与进度；本地下载路径保留可配置回退。

对象存储需要支持 Range、对象生命周期和签名过期。签名地址不能绕过用户归属与流量额度：保留必要预留，按可信访问日志/回调对实际传输进行去重结算，覆盖 Range、重复请求与延迟日志；在这条链路验收前不切换正式下载出口。

优先验证云厂商支持的同地域云内上传路径，并确认是否绕过实例公网 10Mbps 限速及其计费规则；不能只因对象存储“同地域”就认定上传一定不走公网。对象存储给用户分发消耗的是对象存储侧带宽和流量费用。

若成品上传仍走公网，首次上传继续占用 10Mbps，采用已有阶段准入控制，成品大文件公网上传同时先限 1 路；不再新增独立调度平台。ASR 使用既有短分片串行上传，优先使用供应商支持的同地域接口及合规压缩音频格式，不把长音频完整转成巨大 WAV 后一次上传。若供应商必须使用 PCM，则逐片生成、上传并释放；通过简单分片缓冲控制本地峰值。

压测核算对象存储上传、ASR 上传和本地下载回退的合计出站，给 API/SSE 留出响应余量。对象存储解决应用出口的文件分发竞争，不承诺消除首次取源和上传成本。尚未接入对象存储时，所有本地成品下载仍共享 10Mbps，属于明确的过渡期限制。

### 6.3 控制机制收敛

保留已有授权与结算、SSRF 检查、浏览器隔离、明确时限、进程组 Watchdog、磁盘配额和终态 CAS。每项只在正确层执行，减少重复探测与全量扫描。

platform 来源只使用现有 Redis 协调；legacy 如继续兼容则保留独立本地策略，不叠加。只有明确连续风控/限流才启动来源冷却，阈值先保留 3 次，冷却先测 60 秒；尊重有效 Retry-After。普通网络失败不扩散为全平台冷却。

不新增通用策略平台、多级重试、全文件重复校验、自研下载器或 Kubernetes。render 独立 Worker 本身限制重 CPU 并发，不再同时增加第二套 Redis 重转码信号量。

## 7. 部署与容量建议

**当前正式部署基线：轻量云 4 核 / 8GB / 10Mbps，1 个 API 进程，6 个 Solo Worker，远程 ASR/LLM，同云同地域对象存储。** 实际运行并发按下表及整机压测结果确定。

先在隔离环境逐步启用上述实例并记录整机峰值。整机常见工作负载的内存目标先控制在约 6GB 以内，给系统、突发浏览器响应及页缓存保留约 2GB；这是观测目标，不给每个进程硬套相同内存上限。不能靠持续 swap 或进程被杀来维持标称并发。Chromium 同时 1 项、重渲染同时 1 项；没有本地 ASR/LLM 大模型常驻。

FFmpeg 重处理先用 2 个有效线程，不开启全部核心自动线程，也不同时增加转码任务数；若实际浏览器与转码共存使 API 延迟明显上升，再对照测试 1 线程。轻量云需观察长时间任务的 CPU 基线、突发积分或厂商限制，不仅做数十秒短测。M1 8GB 开发环境可用更少实例验证同一流水线，不要求与线上实例数量一致。

| 项目 | 起点 | 扩容依据 |
| --- | --- | --- |
| control / media / asr / llm / render 槽位 | 1 / 2 / 1 / 1 / 1，共 6 个 Solo 实例 | 各阶段实际等待和整机资源峰值 |
| 每任务 ASR / LLM 分段并发 | 1 / 1，独立任务可重叠调用 | 供应商 RPM/TPM、任务吞吐和延迟；许可后再测分段 2 |
| 视频重处理 | 同时 1 项，先测 2 线程 | CPU、内存、渲染等待 |
| 浏览器取源 | 同时 1 项 | 内存、来源成功率和风控 |
| 来源缓存 | 最长 120 秒 | 地址签名和会话有效期 |
| 本地临时总配额 | 5GB | 并发阶段真实峰值；需要提高时单独调整容量约束 |
| API 进程 | 1 | 先避免复制进程内缓存与连接池，按实际请求延迟评估 |
| 内存观测目标 | 常见峰值约 6GB 以内，不持续换页 | 包含 API、数据库、Redis、Worker、浏览器与 FFmpeg |
| 成品公网大文件上传 | 同时 1 路；云内路径另按实测 | 与 ASR、本地下载回退共同核算 10Mbps 出口 |

10Mbps 理论合计约 1.25MB/s，100MB 文件即使独占出口也至少约 80 秒；5 人均分约 250KB/s，10 人均分约 125KB/s，未计协议开销。这是本地交付或公网上传的传输耗时/速率估算，不是源站入站速度估算。对象存储直接分发后，用户成品下载不再平分该实例的 10Mbps；首次公网上传及 ASR 上传仍按上文处理。

在固定机器内先调整资源分配：媒体槽维持 2、不再增加分片数；文本等待且内存有余量时 LLM 从 1 测到 2；重处理始终 1。源站受限或出口饱和时不加 Worker。先复用缓存、优化云内传输与供应商配额；若持续超出这台机器容量，单独评估扩容，不把它作为首期方案的默认依赖。

后续确需跨机器时，阶段输入、检查点、上传原件及输出必须使用共享可访问存储，不能让下一节点拿到仅存在上一节点的本地路径。初期不启用自动扩容。

多进程发布时同时核算数据库连接：Worker 连接池建议先用 pool_size=2、max_overflow=1，API 按请求量单独配置，使总连接预算留有恢复和管理余量。事务和查询限时与健康检查分开设置，健康检查仍保持不超过 1.5 秒；不让增加进程隐式放大连接数或把数据库短锁等待误记成模型超时。

## 8. 实施工作包与交付边界

工作包是本方案内部拆分，不替代项目已有开发阶段；每包实施须在获准范围内，仅修改 backend/，本轮不跨入 frontend/。

| 工作包 | 交付内容 | 完成条件 |
| --- | --- | --- |
| A：确认基线并修正超时 | 失败任务诊断、有效配置核对、分阶段耗时日志、统一调用预算、兼容现有工作流 | 可定位真实超时层；支持范围内长视频不被冲突的短预算截断 |
| B：可恢复并行与已有结果复用 | 阶段数据迁移、统一派发、释放槽位、ASR/LLM 检查点、成品/文稿/AI 复用、发布/清理并发修正、账号并发 | 两个下载可重叠，下载与文本 AI 可同时执行，缓存命中不重做，阶段恢复只结算一次 |
| C：10Mbps 文件分发与下载提速 | 同云同地域对象存储及流量结算、云内上传验证、可复现来源缓存、受控双路传输、兼容 MP4 快捷交付、轻量容量检查 | 用户直接从对象存储取成品；首次上传路径与速率已实测；无缓存样本质量不降低 |
| D：固定机器多用户验收 | 1/2/5 用户混合负载、10 人突发、6 个独立服务实例、长时间内存/CPU/带宽测试 | 公布现有 4 核 / 8GB / 10Mbps 的实际等待、吞吐和承载边界 |

双 Worker 同队列仅可作为 B 包内部的验证步骤，不单独发布为长期方案。A 包的预算代码可先交付；整体上线以阶段恢复、资源隔离和对应验收通过为准。

新增范围预计涉及 tasks、billing、download、transcript、ai、clips、video、storage、queue、config、Alembic、部署模板与必要回归测试。跨模块通过 Service/Repository/Protocol，阶段推进和结算归 TaskService 管理。

每包维护宿主机与容器环境模板；以 uv 管理依赖。每包运行 uv run pytest，交付修改文件清单、启动命令、curl/Swagger 验证步骤及测试结果。方案文档本轮只做内容与格式检查，不将 pytest 历史结果作为本次验证。

## 9. 验收指标与回退

### 9.1 测量口径

分别记录 HTTP 受理、首个有效阶段开始、每阶段排队、来源访问、传输、预处理、ASR、Map/Reduce、成品上传和用户下载时间。父阶段与子阶段有重叠时不能直接相加。

缓存命中、来源缓存命中和完全冷任务分组统计；区分同时处理不同内容与多人请求相同内容。先固定来源、清晰度、模型与输出参数，再比较并发与线程配置。

建议目标为：在实测可承载负载内 HTTP 受理 p95 ≤ 1 秒、首个有效阶段排队 p95 ≤ 2 秒。首期核心场景是两个媒体传输 + 一项远程 ASR + 一项文本 AI 可重叠，重处理需要时单独推进；对应业务任务数取决于阶段依赖。不能据此推导十个冷长视频全程无等待。1/2/5 用户逐档报告各阶段等待，10 人突发观察恢复与队列消退；达不到目标时公布实际容量，不通过仅设置 running 达标。

### 9.2 必须通过的场景

- 20/40/60 分钟样本：有字幕、无字幕、已有文稿、MP3、横竖屏及需转码来源。
- 两个下载、下载 + 总结、长 ASR + 短问答、两个不同用户、单用户连续提交；确认是否存在饥饿，必要时再做简单用户轮转。
- 三平台固定样本与长视频多用户混合负载，报告耗时、峰值内存、本地空间、带宽、供应商响应及失败率。
- 单片慢响应、模型超时、429、连接错误、预算不足及真正整体截止；已完成检查点可复用，最终状态不伪成功。
- 取消一个任务不影响其他任务；Worker 异常不清理其他执行；重复消息和恢复不重复结算。
- SSE 超过 5 分钟、页面断连后恢复；连接问题不被记成处理失败。不同阶段共用父任务的原子 seq，重新订阅仍先订阅后快照，避免阶段切换产生进度倒退或遗漏。
- 对象存储 Range/重试/签名过期/上传失败/流量结算；缓存访问按用户授权。
- 文件完整性、画幅、时长和音视频轨验证，交付样本进行完整解码。

### 9.3 发布与回退

使用独立测试账号、队列和存储做真实媒体验证，付费模型验收按获准预算执行。先小流量发布，再对照基线扩大。

流水线切换采用任务执行版本：在途旧任务由旧版本完成，新任务使用新版本；回退停止新版本准入，等待或取消对应执行，保留检查点。阶段数据库迁移采用兼容增加，不能让旧代码误消费新阶段消息。

来源缓存、双路下载和快捷交付可分别关闭；对象存储故障可按配置回到已有本地交付。回退 Worker 数量前先停止接新消息并处理在途进程，不强制丢弃任务目录。

## 10. 定稿时仍需核实的输入

实施 A 包时收集即可，无需为制定本方案提前停止：

1. 一个真实失败任务的 task_id、错误码、视频长度及阶段耗时，确认线上故障原因。
2. 已确认 4 核 / 8GB / 10Mbps；补充可用盘、出入站限速规则、实例持续 CPU 表现，以及 API/Worker 有效超时配置。
3. ASR/LLM 供应商的并发、RPM/TPM、音频上传与上下文限制。
4. 首个正式业务负载：按 1/2/5 人逐档起测，再测 10 人突发，记录视频大小与时长分布、下载/AI 比例和缓存命中率。
5. 云厂商和地域、对象存储的云内上传路径、流量预算与可信传输日志能力；先做适配器与验收，账号购买和上线配置另按明确授权执行。

本版收敛为一个架构、一套截止时间、一套阶段恢复机制。性能收益和多用户容量由后续验证给出，不以放大超时或增加进程数代替验收。
